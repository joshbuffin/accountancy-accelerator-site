Build your management accounts system.

This prompt has Claude Code build you a complete management accounts production system, branded as your firm. Once it's built, producing a pack for a client comes down to: export from your accounting software, drop the files in a folder, type one command, review the PDF.

Claude calculates the numbers with code (never by guessing), checks that everything reconciles, writes the commentary in your firm's voice, and produces a polished PDF with charts, KPIs, a P&L and a balance sheet.

Overview

How the system works

There are three levels, and you only do the first one once:

1

Build it once. Paste the prompt below. Claude sets everything up, tests it on a fictional demo client, and you give it design feedback until you love the look. Allow 2 to 3 hours, across one or two sittings.

2

Onboard each client once. For each new management accounts client, type /mgmt-new-client. Claude asks you about 15 questions (one at a time), recommends which pages to include, generates the first pack, and then writes a checklist of exactly what to post and export for that client every period. About 30 to 60 minutes per client.

3

Produce each pack. Each month or quarter, work through the client's checklist, export the reports, and type /mgmt-pack. About 15 to 30 minutes, plus your review.

Treat it as a starting template. What Claude builds will be good out of the box, and it gets better every time you ask for a change, because improvements are built into the system rather than into one client's pack.

What you'll end up with

What Claude will build

The engine. Code that reads your exports, runs the analysis, checks it reconciles, and prints a branded PDF.

Your brand file. One file holding your colours, fonts, logo, footer and disclaimer. Change it once and every pack updates.

A library of pages. Cover, contents, KPI dashboard, executive summary, revenue, gross margin, costs, payroll, cash, debtors, creditors, director's loans, targets, P&L, balance sheet and notes. Switch each one on or off per client.

Automatic reconciliation checks. Before any PDF is produced, it checks the balance sheet balances, profit agrees to the ledger, the comparative columns are on the right basis and no page is blank.

Client template and commands. A config file for each client, an onboarding runbook, and three commands: /mgmt-new-client, /mgmt-pack and /mgmt-help.

Preparation

Before you start

Do Guide 1 first. You've completed Teach Claude about your firm, so Claude already knows your firm and tone of voice.

Use the same folder. You're in the Claude desktop app's Code tab, working in the same folder you used for Guide 1 (Local environment, your Firm AI folder).

Have your branding to hand. Your logo as a PNG or SVG file, and your brand colours (hex codes if you have them).

Optional, but very useful: sample exports. Export a General Ledger Detail and a Balance Sheet from Xero's Demo Company (or your own firm's books) and save them in your folder. Claude will match the engine to the exact format of your exports. Don't use real client data while building.

Node.js will be needed. If you don't have it, Claude will walk you through installing it.

# MANAGEMENT ACCOUNTS SYSTEM: BUILD BRIEF FOR CLAUDE CODE

## PART 1: INSTRUCTIONS FOR CLAUDE (do not edit this part)

I want you to build a management accounts production system for my accountancy practice, inside this folder. When it is finished, I should be able to take a client's exports from our accounting software, drop them in a folder, run one command, and get a professional, branded PDF management accounts pack with charts, KPIs, a P&L, a balance sheet and written commentary. My firm's details and branding are in Part 2.

You already know my firm from CLAUDE.md and the context/ folder. If those don't exist yet, tell me and suggest I run the firm setup prompt first, but carry on if I say so.

Work through the stages below in order. At the end of each stage, stop, tell me in plain English what you've done and what I should check, and wait for me to say "continue" before starting the next one. I may not be technical, so explain anything I need to do (installing something, approving something) step by step.

### NON-NEGOTIABLE PRINCIPLES (apply to every stage)
1. Numbers come from code, never from you. Every figure in a pack is calculated by scripts that read the exported data. You never type, estimate or "read off" a number yourself. Your role in each pack is the written commentary, and the commentary may only quote figures the scripts produced.
2. Never invent data. If something is missing (an export, an account mapping, a target), stop and ask, or mark it [TODO]. Never fill a gap with a guess.
3. Every pack must reconcile before it is shown to me. The engine runs automatic checks and prints a pass/fail report (see Stage 2). A failed check is never silently ignored.
4. Configuration over code. Anything that differs between clients (names, accounts, pages, targets, notes) lives in that client's config file, not in the code. The code stays general so every client benefits from improvements.
5. Client data stays local. Client exports and packs stay inside this folder. Nothing is uploaded anywhere. If this folder is a git repository, add the clients/ data folders to .gitignore.
6. The PDF is the deliverable. Never suggest sending HTML or raw files to a client.
7. Draft, don't send. You never email a pack to a client. A qualified person in my firm reviews and sends it.

### STAGE 1: SET UP AND BRANDING
1. Check that Node.js (version 20 or later) is installed. If it isn't, walk me through installing it from nodejs.org, then check again.
2. Create this structure:
   management-accounts/
     engine/            the code that reads exports, does the analysis and builds the PDF
     brand/             my logo and brand settings (brand.json)
     templates/         the client config template and the onboarding runbook
     demo/              a fictional demo client used for testing
   clients/
     _template/         a blank client folder to copy for each new client
3. Set up the engine as a Node.js project and install what it needs: a spreadsheet reader for .xlsx and .csv files, a YAML or JSON parser for configs, and Puppeteer to turn HTML into PDF. Draw charts as inline SVG generated by the code, so there are no external chart services and nothing to break.
4. Create brand/brand.json from my answers in Part 2 (firm name, colours, fonts, logo path, contact details, footer, disclaimer, number and date formats). Every page of every pack must read its styling from this file, so I can rebrand everything by editing one file.
5. If I've said I'll provide a logo, tell me exactly where to save it (brand/logo.png or brand/logo.svg).

### STAGE 2: BUILD THE ENGINE, TESTED ON A DEMO CLIENT
1. Create a realistic FICTIONAL demo client in demo/ (a made-up limited company) with fake exports in the same format as my accounting software produces (see Part 2): a General Ledger detail export covering at least 24 months and a Balance Sheet export with a prior-year comparative. Make the data believable: seasonality, a couple of cost lines creeping up, some debtors over 60 days, an overdrawn director's loan.
2. Build the engine in clear, separate steps, so each one can be tested on its own:
   - Parse: read the exports into clean data (account code, name, type, date, amount). Read the account type (revenue, direct costs, overheads, assets and so on) from the export wherever it's available, rather than asking me to map every nominal by hand.
   - Analyse: calculate everything the pages need (period, year-to-date and prior-year figures, monthly trends, margins, KPIs, variances).
   - Check: run the reconciliation checks below.
   - Narrative: save the key figures and movements to a summary file that you (Claude) read to write the commentary (see Stage 4).
   - Render: build the HTML pages from the analysis and brand.json, then print to PDF with Puppeteer.
3. Build these page types. Each one is a "section" that can be switched on or off per client, and sections appear in the order listed in the client's config:
   - cover: firm logo, client name, period, report title, prepared-by line
   - contents: auto-generated from the sections included
   - kpis: a one-page dashboard of headline numbers with movement against the prior period and prior year
   - exec-summary: the written commentary (headline, what went well, what to watch, recommended actions)
   - revenue: revenue trend and breakdown by income account
   - gross-margin: gross profit and margin % over time (only if there are direct costs)
   - cost-analysis: overheads by category, biggest movements, and flagged "watched" costs that are creeping up
   - payroll: staff costs trend and as a % of revenue
   - cash: bank balance trend and simple cash movement
   - debtors: aged debtors (current, 30, 60, 90+ days), debtor days, largest balances (anonymised to initials if I choose)
   - creditors: aged creditors and named key suppliers
   - directors-loans: director's loan account balance over time, with an optional s455 exposure note when overdrawn
   - targets: progress against a revenue or profit target for the year, with a straight-line pace marker
   - pnl: a profit and loss statement for the period, year to date and prior-year comparatives
   - balance-sheet: the balance sheet at period end against the prior-year comparative
   - notes: basis of preparation and the disclaimer from brand.json
4. Reconciliation checks. The engine must check these on every run and print a clear PASS or FAIL list, and it must refuse to produce a final PDF on a FAIL unless I explicitly say to override it (and if I do, add a visible draft watermark):
   - The balance sheet balances (net assets equal total equity).
   - The profit for the year to date in the analysis agrees to the current-year earnings line on the balance sheet export (within £1).
   - The total of every P&L category in the analysis agrees to the general ledger.
   - The period requested is fully covered by the general ledger export, and the GL starts early enough to build every prior-year comparative and trend chart (warn if it covers less than 24 months).
   - The balance sheet comparative column is the same date one year earlier (not the prior quarter or month), so prior-year figures can't appear under the wrong heading.
   - No section included in the pack is empty. A blank page reads as unfinished.
   - A suspense or unreconciled-items balance is flagged as a warning.
   - Stock: if a stock or inventory page is on, and the closing stock balance hasn't moved for 3 or more months, warn that the stock journal probably hasn't been posted and margin may be wrong.
5. Generate the demo pack with one command (for example: node management-accounts/engine/generate.js --client demo --period 2026-06) and open the PDF for me.
6. Design standard: it should look like a premium report, not a spreadsheet. Use plenty of white space, a consistent grid, the brand colours used sparingly (headings, chart highlights, key numbers), clean sans-serif body text, numbers right-aligned in tables, negatives in brackets, page numbers and the firm name in the footer, and every chart titled with a one-line takeaway (for example "Revenue up 12% on last year"), not just a label. A4 portrait unless I say otherwise in Part 2.
Then stop and ask me for design feedback. Expect a few rounds of changes; make each one in brand.json or the shared styles so it applies to every client.

### STAGE 3: THE CLIENT TEMPLATE AND ONBOARDING RUNBOOK
1. Create clients/_template/config file (a YAML file, with a comment against every field explaining it) holding:
   - name, display name on the cover, legal name, financial year start month, reporting cadence (monthly / quarterly / annual), audience (who reads the pack and how financially literate they are)
   - the ordered list of sections to include
   - revenue accounts, the north star metric the owner cares about most, any revenue split (by channel, location or tracking category)
   - direct-cost and payroll accounts (confirmed from the GL, not typed out by hand), and "watched" cost accounts to flag for creep
   - targets (financial-year or calendar-year revenue or profit target), and decision rules ("if X happens, recommend Y")
   - debtors on or off, key suppliers, stock on or off, director's loan accounts and whether to flag s455
   - standing advisory themes to comment on every period, and sensitivities (things NOT to over-flag)
   - a periodPrep checklist (see point 3)
   Each client also gets a notes section, in plain English below the config, for anything the analyst should know.
2. Create templates/onboarding-runbook.md: a step-by-step guide that you follow whenever I onboard a new client:
   - Step 1, scope: ask me the scoping questions below ONE AT A TIME, then write the client's config. Don't ask anything the general ledger will tell you (nominal codes, cost classifications, payroll lines, supplier names, DLA accounts): read those from the data and ask me to confirm them. Focus your questions on what the data can't tell you. The scoping questions are:
     1. Trading name, and exactly how it should appear on the cover?
     2. Which month does their financial year start?
     3. Who reads the pack, and how much accounting do they understand?
     4. How often will we produce it: monthly, quarterly or annual?
     5. What does the business sell, and does it hold stock?
     6. What's the one number the owner checks first?
     7. Is revenue split by channel, location or product, and how is that tagged in the books? Do they care about customer concentration?
     8. Which cost lines should we spotlight or watch for creep? Is anything misclassified in the books?
     9. Are any costs recharged to their customers?
     10. Do they have a revenue or profit target? Financial year or calendar year?
     11. Any decision rules worth checking every period (for example "hire when revenue covers costs plus a salary")?
     12. Do debtors and creditors matter? Any key suppliers to chart?
     13. Do they hold stock, and is a closing stock journal posted each period?
     14. Standing advice themes the owner cares about?
     15. Director's loans, what's posted at period end (depreciation, accruals, prepayments, stock, tax), and anything we should be careful not to over-flag?
     Then read the config back to me and confirm.
   - Step 2, pick the pages: recommend a section list based on the answers (for example a product or retail business needs gross margin and stock; a services business with recurring fees needs recurring revenue, debtors and targets), then let me add or remove pages. Never include a page that would be blank.
   - Step 3, prep and import: tell me exactly which adjustments to post and which exports to pull, with the report name, date range, comparative basis and file format for each one, and the folder to save them in: clients/<client>/input/<period>/.
   - Step 4, generate: run the engine, show me the reconciliation check results, then open the PDF.
   - Step 5, revise: sort each change I ask for into one of three buckets, preferring A, then B, then C: (A) data or wording: change the client config only; (B) a new capability: build it into the engine and switch it on per client, so other clients' packs don't change; (C) a bespoke layout: a per-client template override, only as a last resort. Regenerate and repeat until I sign it off.
   - Step 6, lock the checklist: once the first pack is signed off, write the client's periodPrep checklist into their config, based on what the build actually proved was needed (not just what I said at the start). It has two lists:
     (a) adjustments: what must be posted or checked in the accounting software before exporting (closing stock, depreciation, accruals and prepayments, DLA, bank reconciliation, clearing suspense). Each one has a frequency, which is how often the journal must be posted. If any page charts a monthly trend of a balance (stock, cash, DLA), the journal must be posted monthly, even if the pack is quarterly; otherwise the chart shows a false "step". Mark an item "blocking" if the pack would mislead without it, and say why.
     (b) exports: exactly what to pull each period: the report's real name, the date range (the GL should start about 24 months before period end), the comparative basis ("period end and same date prior year"), the format, and any gotchas. Also list what is NOT needed, so nobody wastes time exporting it.
     From then on, each period is just: work the checklist, export, generate, review, send.
3. Create clients/_template/ containing the blank config plus empty input/ and output/ folders.

### STAGE 4: COMMENTARY
The written commentary (exec summary, chart takeaways and recommended actions) is written by you, Claude, inside Claude Code, during each pack run, so no separate API key is needed:
- The engine writes a summary file of the key figures, movements, check results and the client's advisory themes.
- You read it, together with the client's config and notes, and write the commentary to a narrative file in the client's output folder in a fixed structure: a lead paragraph, 3 to 5 wins, 3 to 5 things to watch, and 3 to 5 recommended actions.
- Then the engine re-renders the PDF with the commentary included.
Commentary rules: use the tone of voice in context/tone-of-voice.md and the commentary style in Part 2; write for the audience in the client's config; quote only figures in the summary file; be specific and practical ("debtors over 60 days rose to £14,200; chase the two largest balances"), never generic; flag anything technical (tax, s455, reliefs) as something to discuss with the client manager; respect the client's sensitivities.

### STAGE 5: COMMANDS SO I NEVER HAVE TO PASTE THIS AGAIN
Create these Claude Code slash commands in .claude/commands/:
- /mgmt-new-client: runs the onboarding runbook (Steps 1 to 6) for a new client.
- /mgmt-pack: produces a pack for an existing client. It asks which client and which period, shows me that client's periodPrep checklist and confirms each blocking adjustment has been posted, checks the exports are in the right folder, runs the engine, writes the commentary, re-renders, shows me the check results and opens the PDF. Then it asks if I want any revisions (following the A/B/C rule).
- /mgmt-help: explains in plain English how the system works, the folder structure, the commands, and what to export from my accounting software.
Then add a short "Management accounts" section to CLAUDE.md pointing to these commands and the principles above.

### STAGE 6: HAND OVER
- Generate the demo pack one final time and confirm every check passes.
- Write management-accounts/README.md: a plain-English guide to the system (folders, commands, how to rebrand, how to add a page type, troubleshooting).
- Give me a short summary of what's been built, how to onboard my first real client, and a list of anything in Part 2 that's still [TODO].

1

Ask you about 15 questions, one at a time. The business, who reads the pack, the number the owner cares about most, targets, debtors, stock, director's loans, and anything to be careful about. Creating a new pack

Every period after that

1

Close the period. Work through the client's adjustments checklist in your accounting software: bank reconciled, suspense cleared, closing stock, depreciation, accruals and prepayments, and anything else on their list. If an item is marked blocking, don't generate the pack until it's posted.

2

Export the reports. Pull the reports on the client's checklist. For a typical Xero client that is:

General Ledger Detail, from about 24 months before the period end to the period end, exported to Excel. The 24 months of history are what build the prior-year comparatives and trend charts.

Balance Sheet as at the period end, comparing with the same date one year earlier (not the previous quarter or month), exported to Excel.

Aged Receivables Detail at the period end, if the pack has a debtors page.

Aged Payables Detail at the period end, if the pack has a creditors page.

3

Save them in the client's input folder: clients/<client name>/input/<period>/, for example clients/acme-ltd/input/2026-06/.

4

Run the pack. Type the command below. Claude checks the checklist, runs the engine, writes the commentary and opens the PDF.

/mgmt-pack
5

Review it properly before anything goes to the client:

Every reconciliation check shows PASS.

Profit for the period agrees to the P&L in your accounting software.

Net assets agree to the balance sheet in your accounting software.

The client name, period and dates are correct on the cover.

The commentary is accurate, makes sense for this client, and says nothing you wouldn't say yourself.

No page is blank or half-empty.

6

Ask for revisions. Just say what you want changed, for example "make the debtors page show the top 10 balances" or "add a note that the VAT bill is due in August". Claude decides whether it's a one-client change or an improvement for every client.

7

Send it. Once a qualified member of your team has reviewed it, send the PDF yourself or walk the client through it on a call. Claude never sends it.

Good to know

Lessons we learned building ours

Code calculates, Claude comments. Claude writes the commentary, but every figure must come from the scripts. This is what makes the packs trustworthy.

Watch the stock journal. The most common error is an unposted closing stock journal. Gross margin looks great because purchases are being reported, not cost of sales. The stock-movement check exists for this reason.

Post journals as often as you chart them. If a page charts a monthly trend (stock, cash, director's loan), the journal has to be posted monthly even if the pack is quarterly. Otherwise the chart shows a flat line and then a cliff, which looks like real trading.

The quiet errors are the dangerous ones. A Balance Sheet export compared with the previous quarter instead of the previous year will build fine, with the wrong figures under the prior-year heading. The comparative check catches it.

Export 24 months of ledger. A ledger export covering only the current period builds fine but leaves every trend chart empty.

Lock the checklist after the first build, not before. What a client manager says is posted at period end, and what the ledger actually shows, are often different. Build the checklist from the evidence after the first pack.

No blank pages. A half-empty page looks unfinished. Only include pages the client's data can fill.

Check

If something goes wrong

A check fails. Read the message: it says what doesn't agree. Usually it's an export with the wrong dates or comparative, or an adjustment that hasn't been posted. Fix the source and run /mgmt-pack again.

A page is blank or a number looks wrong. Ask Claude: "Why is the debtors page empty for this client?" It will look at the data and config and explain.

An error message or crash. Tell Claude what went wrong in plain English. It can read the error and fix it.

You're not sure what changed. Packs are built from your files, so nothing is lost. Ask Claude to regenerate.
